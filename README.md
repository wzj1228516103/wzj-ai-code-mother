# `wzj-ai-code-mother` 基于 Spring Boot 3 + LangChain4j + Vue 3 的企业级 AI 代码生成平台设计与实现 README

## 一、项目简介

`wzj-ai-code-mother` 是一个基于 **Spring Boot 3 + Vue 3 + LangChain4j** 的 AI 代码生成平台。

项目的核心目标是：让用户通过自然语言描述需求，系统自动完成应用创建、AI 对话式生成代码、页面预览、应用部署、代码下载和后台管理等流程，尽量降低前端页面开发门槛，提高原型开发效率。

本项目当前阶段以 **单体版本落地** 为主，同时预留了 **微服务拆分结构**，便于后续继续扩展。

## 三、项目目标

本项目希望实现一个“AI 辅助生成网页应用”的平台，主要解决以下问题：

- 用户不会写前端页面，仍然可以通过自然语言描述生成网页应用
- 用户生成后可以继续和 AI 对话，不断修改页面
- 生成结果不仅能看，还能部署、下载、管理
- 管理员可以对用户、应用、对话记录进行统一管理

一句话概括：

> **这是一个面向网页应用生成场景的 AI 代码生成与管理平台。**

## 五、系统主要功能模块

从业务角度看，项目主要由以下模块组成：

1. **用户模块**：注册、登录、注销、获取当前登录用户、管理员管理用户
2. **应用模块**：创建应用、修改应用、删除应用、查询应用、精选应用展示
3. **AI 生成模块**：根据提示词生成代码，支持流式输出
4. **对话历史模块**：保存用户和 AI 的对话记录，并支持分页/游标查询
5. **预览与部署模块**：生成后预览页面、部署应用、下载源码、生成封面图
6. **后台管理模块**：管理员管理用户、应用、对话记录
7. **扩展架构模块**：预留微服务拆分能力

## 八、一个原先无法实现、后来实现了的功能

这一部分用于回答老师的第三个问题：

> **“描述一个你原先无法实现的功能，后来实现了，在这个过程中的思路是什么？”**

我准备回答的功能是：

# **AI 对话流式生成代码，并在前端实时展示**

### 1. 最开始遇到的问题

一开始我想做的是：用户输入一句需求，后端调用 AI，等 AI 全部生成完成后，再把结果一次性返回给前端。

但这种做法很快暴露出几个问题：

- AI 生成代码耗时较长，用户等待体验差
- 如果一次性返回大量文本，前端无法实时感知生成过程
- 用户看不到系统在“思考”什么，交互体验很生硬
- 如果生成失败，不方便定位是哪个阶段出了问题

也就是说，**同步返回虽然简单，但不适合 AI 大段内容生成场景**。

### 2. 我的思路转变

后来我把问题拆开来想：

1. 后端不要等所有结果都生成完再返回
2. AI 只要生成一部分内容，就立刻推送给前端
3. 前端边接收边渲染，形成“实时输出”的效果
4. 用户消息和 AI 回复还要能落库，保证会话可追踪

于是我把这个功能从“普通接口返回”改成了“**SSE + 流式处理**”的实现思路。

### 3. 具体实现思路

我后来的实现方案大致如下：

#### 后端部分

- 使用 `Reactor Flux` 作为流式数据载体
- 在接口层提供 SSE 输出接口
- 用户发送消息后，先把用户消息写入对话历史
- 调用 AI 代码生成器，按流返回生成内容
- 使用流处理执行器统一处理生成过程
- 在流结束后，再补充 AI 回复保存、上下文清理等逻辑

#### 前端部分

- 前端发起流式请求
- 收到一段内容，就立刻追加到当前 AI 消息中
- 同时展示“AI 正在思考”状态
- 生成结束后，刷新页面预览或保留最终生成结果

### 4. 这个功能解决了什么问题

实现之后，系统体验提升非常明显：

- 用户不需要长时间空等
- 能实时看到 AI 输出过程
- 对话过程更像真实聊天，而不是传统表单提交
- 更适合长文本、长代码生成场景
- 出问题时也更容易定位是生成中断还是渲染中断

### 5. 这个过程给我的收获

这个功能让我最大的收获不是“把代码写出来”，而是学会了：

- 遇到复杂功能时，先拆解业务问题，而不是直接上代码
- AI 场景和普通 CRUD 场景不同，要重视交互体验
- 后端接口设计要服务于前端体验
- 做项目时不仅要实现功能，还要考虑稳定性、可维护性和用户感受

如果老师问我“这个功能你为什么觉得难”，我会回答：

> 难点不在于调一个 AI 接口，而在于把 **AI 生成、流式返回、前端实时渲染、历史记录保存** 这几件事串成一个完整闭环。
